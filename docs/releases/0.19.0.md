# Voice PE Realtime 0.19.0 — GPT-Live voice runtime (experimental, opt-in)

Add-on version `0.19.0`, 2026-10-14. Full entry in the
[changelog](../../openai_realtime_voice_agent/CHANGELOG.md).

## In one paragraph

The add-on can now run a Voice PE on **OpenAI GPT-Live (`gpt-live-1`)** instead
of the Realtime API. It is **off by default**: `voice_runtime` is unset on every
existing install and nothing changes until you set it. Under
`voice_runtime: live` the add-on routes every request itself (Home Assistant's
local intent engine first, then a Responses backend with the full tool set),
speaks only results a tool verified, knows the home's floors, rooms and exposed
entities, acts on the room of the device that heard you, turns slow requests
into background tasks, and keeps GPT-Live's per-second billing inside on-demand
sessions and a hard daily cap. Realtime (`gpt-realtime-2`) stays the default
and the recommended runtime.

## What is new under GPT-Live

- **Router mode** (`live_router`, on by default inside Live). The add-on, not
  the voice model, decides and runs every tool. Plain device commands go to
  Home Assistant's intent engine, locally, on safe domains only (never locks,
  covers, alarms or scripts); everything else goes to a Responses backend
  (`live_backend_model`) called with the same Home Assistant, web search,
  timer, memory, enrollment, confirmation and agent tools, through the same
  safety gates as Realtime. A success claim with no tool result behind it is
  never played.
- **The backend knows the home.** Home Assistant's exposed-entity overview plus
  the floor and area registries (with aliases) sit in the backend's cached
  prompt prefix, refreshed every 5 minutes and at each wake. Loose wording is
  matched to real names. `live_context_entities` (off by default) adds a short
  state snapshot of up to 30 entities you name.
- **Room from the satellite.** "Turn on the lights" acts on the room of the
  Voice PE that heard it, found from its network address and the device
  registry. A room Home Assistant fills in on its own is not trusted.
- **Optional auto-expose** (`live_auto_expose`, off by default). Controllable
  entities Assist cannot see yet are exposed every 5 minutes; input booleans
  and scripts only when they are on a dashboard; locks never; a deliberately
  un-exposed entity stays un-exposed.
- **A parsed command is never ignored.** When Home Assistant recognised a
  command that could not be carried out, the assistant says it could not tell
  which device you meant, instead of staying silent.
- **Confirmation for risky actions is unchanged.** Locks, garages, gates,
  doors and alarms still need a spoken yes, bound to the exact question that
  asked for it; a state question never runs a control tool; what the parser
  heard reaches the backend as a hint, never as an instruction.
- **Long tasks.** A request that needs a slow tool (an agent turn, a web
  search) becomes a background task after a few seconds (house commands get up
  to 8 s first). The voice says so, the conversation goes on, and the answer is
  delivered when it lands: in the open session, through a short new session
  that passes the spend gate, as an announcement, or by text. Bridges can
  report an accepted task back with `POST /task-result`; see
  [Agent Integration](../agent-integration.md).
- **Cost controls.** A session opens only on a wake and closes after idle
  (10 s), after a reply with no follow-up (8 s), at 45 s with nothing audible
  and at 300 s regardless. Daily caps (`live_max_session_minutes_per_day`,
  `live_max_usd_per_day`; 60 min / $3.00 by default, shared by all devices,
  persisted across restarts) refuse new sessions out loud. Backend tokens
  count against the same cutoff.
- **Fast paths.** Plain chat can skip the pre-result hold through a tiny
  tool-less classifier (`live_fast_chat_model`); clock and person-location
  questions go straight to the matching tool.
- **Acknowledgements.** While a tool runs the voice may say only a short phrase
  from a closed set; a short fallback clip covers silence after about a
  second, starts with a lead burst so a cold speaker does not clip its first
  syllable, and is never followed by a second acknowledgement.
- **Developer hook.** `experiment_mode` (off by default) lets a test rig vary
  timing and model choices without a rebuild; it cannot change any cost bound
  and has no effect on a normal install.

## Fixed in both runtimes

- Action-gate and tool-result handling: a confirmation is bound to the exact
  prompt that asked for it; placeholder tool arguments are dropped before a
  call; tool outcomes are classified before anything is spoken.

## Costs, in plain numbers

GPT-Live is **$0.05 per connected session minute, billed per second, idle time
included**. A session left open would cost $3.00 an hour per device; this
add-on never leaves one open, and the daily cap stops a runaway. The backend
model's tokens, web searches and the fast chat classifier are billed separately
by OpenAI. There is no per-response cost sensor under Live;
`sensor.voicepe_<instance>_live_session_cost_today` reports voice dollars,
session-minutes, sessions, both caps and the remaining allowance. Read
[GPT-Live cost safety](../configuration.md#-gpt-live-cost-safety) before
enabling it.

## Enabling it

On one instance, in the add-on's ⋮ → *Edit in YAML* view:

```yaml
voice_runtime: live
live_acknowledge_gaps: true
```

Restart and read the startup log: it prints the GPT-Live settings, the caps in
force, the parity report and any Realtime-only options that are ignored
(`turn_detection_type`, `vad_*`, `noise_reduction`, `openai_speed`,
`transcription_*`). Live-only voices (`vesper`, `quartz`, …) are set through
`openai_voice: custom` and `openai_voice_custom`. Remove the two lines and
restart to go back; the Realtime path is untouched by the switch. Every
`live_*` option is optional and documented in the
[Configuration Reference](../configuration.md#-voice-runtime-gpt-live-experimental).

## Compatibility

- **Existing installs:** no change. All new options are optional without
  defaults, so an update does not migrate anyone to Live.
- **Firmware:** [voicepe-realtime-firmware](https://github.com/TristanBrotherton/voicepe-realtime-firmware)
  1.3.1 (its current `main`) serves both runtimes; GPT-Live needs no firmware
  change and was tested on it.
- **Home Assistant:** the MCP Server integration as before. Room awareness and
  the household directory read the device, area and floor registries over the
  add-on's Supervisor token; auto-expose writes Assist exposure settings only
  when `live_auto_expose` is on.
- **Agent bridges:** `ask_openclaw` requests now carry `session_key`,
  `answer_only` and `callback_url`; unknown fields are ignored by older
  bridges, so nothing breaks before a bridge is updated.

## Known limitations of the Live runtime

- Experimental. Tool-requirement detection and the acknowledgement grammar are
  conservative English heuristics, not a general intent classifier; unusual
  phrasing can fail closed (the assistant asks or says it could not).
- GPT-Live has no `response.cancel`: a device "stop" drops the remaining audio
  locally, but backend work already started still finishes.
- `output_lead_buffer_ms` defaults to 600 under Live (about 600 ms before the
  first word) because GPT-Live delivers audio at real time.
- No per-response cost sensor (the parity gap `live_acknowledge_gaps`
  accepts).
